# Architecture Overview

## System Shape

```
┌─────────────────┐     ┌──────────────────┐     ┌────────────────┐
│  Telegram Bot   │     │  Fastify Server  │     │   React App    │
│  (Grammy)       │────▶│  (API + Static)  │◀────│  (Vite, /game) │
│  src/bot/       │     │  src/server.ts   │     │  src/frontend/ │
└────────┬────────┘     └────────┬─────────┘     └────────────────┘
         │                       │
         │              ┌────────┴─────────┐
         │              │     MongoDB      │
         └─────────────▶│  (Typegoose)     │
                        │  src/common/     │
                        └────────┬─────────┘
                                 │
              ┌──────────────────┼──────────────────┐
              │                  │                  │
     ┌────────┴────────┐ ┌───────┴────────┐ ┌───────┴────────┐
     │  TON Blockchain │ │  Telegram      │ │ Stability AI + │
     │  (donations,    │ │  Stars         │ │ OpenAI + IPFS  │
     │   NFT minting)  │ │  ($CUBE topup) │ │ (pass forging) │
     └─────────────────┘ └────────────────┘ └────────────────┘
```

- **Telegram bot** runs on Node.js (TypeScript, ESM) using Grammy for updates.
- **HTTP server** is Fastify with `@fastify/middie` (for Vite middleware in dev mode).
- **Data** is stored in MongoDB via Mongoose/Typegoose with decorator-based schemas.
- **Frontend** is a React 19 + Vite app under `src/frontend` (separate `package.json`),
  served under **/game**; a static multi-page landing (generated by
  `scripts/build-landing.ts`) owns the root.
- **$CUBE is DB-only:** `User.votes` (cache) + the append-only `Balance` ledger (truth)
  are canonical. There is no on-chain jetton and no external money rail.

## Startup Flow

`src/main.ts` orchestrates startup in order:
1. Connect to MongoDB
2. Create bot instance (register middlewares and features)
3. Initialize default balance records if empty + run the claim-uniqueness migration
4. Sync bot commands and the Mini App menu button (non-fatal)
5. Create Fastify HTTP server (register all API handlers)
6. Register shutdown handlers (SIGINT/SIGTERM)
7. `STAGING=true` → just listen (no Telegram engagement, no tx loop) — used by the API
   smoke test; the real staging bot runs with it off
8. Otherwise: start the TON transaction watcher (donations → $CUBE), then the bot
   (polling in dev, webhook in prod)

## Key Runtime Flows

### The mint pass flow (the product)
1. **Source image** — `POST /api/mint/avatars` lists the user's Telegram profile photos
   as previews; `/avatar/select` or `/avatar/upload` (multipart, JPEG/PNG ≤ 8 MB)
   normalizes the source to a 640×640 PNG via jimp and stores it under `data/<name>/`.
2. **Paid tries** — `POST /api/mint/generate` debits `GENERATION_TRY_COST_VOTES` through
   an overdraft-safe CAS (`debitVotes`, `BalanceChangeType.Generation`), runs Stability
   pixel-art img2img + a ChatGPT description, and persists a private draft. A generation
   failure refunds the try. There is no eligibility floor — pay-per-try is the anti-spam.
3. **Submit** — `POST /api/mint/submit` (requires a draft + a bound wallet) flips the
   user to `Submited` and pushes the image to every `BOT_ADMINS` chat with
   ✅ Approve / ❌ Decline inline buttons (notify failures never fail the submit).
4. **Verdict** — Approve: CAS `claimUserForMint` (double-approve mints exactly once) →
   IPFS pin → NFT deploy (mint-before-flip) → `markUserMinted` → referral reward →
   user notification. Decline: state → `Rework`, user may regenerate and resubmit
   (spent tries stay spent).
5. **Gate** — `POST /api/mint/status` drives the whole webview state machine (images
   returned as base64 data URLs); minted users see the Pass view ("World I coming soon").

### Bali windows
Every place is one game-theory engine reading the pass's 120 on-chain traits
(`User.pass.traits`, fetched from the item content JSON at `/api/pass/select`,
backfilled by `/api/world/state`). One `Visit` per holder per 8-hour window
(`windowId = floor(now / 8h)`, UTC). Stake is debited on commit via `debitVotes`
(`BalanceChangeType.Stake`), payout credited once at resolution (`Payout`; refunds
are positive `Stake` rows). Places and numbers: `src/game/places.ts` (14 places, 8
open). Engines are pure: `src/game/engines/{minority,split-steal,commons}.ts`.
Resolver: `src/game/resolver.ts` (pure, DI) + `resolver-start.ts` (60 s tick, not in
STAGING mode) — claims a `Window` lock, CAS-resolves each visit before paying
(at-most-once), bumps `User.rep`, notifies via bot (non-fatal). API:
`/api/world/state|visit|history` (holder-gated, 403 `holder_required`) and public
`GET /api/world/pass/:index`. Deep links: `startapp=bali_<place>` and
`startapp=meet_<inviteCode>` (Canggu pair invite). Admin `/resolve` forces the
current window on staging/dev only.

Sequence: visit → debit → `Visit` row → tick → `claimWindow` → engines →
`resolveVisitOnce` → `addPoints` → `bumpRep` → `setPool` → notify →
`markWindowResolved`.

### $CUBE faucets
- **Daily claim** — `POST /api/users/claim`: initData validation → per-user in-process
  lock → streak multiplier → `addPoints`.
- **Referrals** — `/start` param or `referId` on login stores `referalId`; the referrer
  is credited `REFERRAL_MINT_REWARD_VOTES` when the invitee's pass is minted (inside the
  approve path — human-gated, so unfarmable; non-fatal; at-most-once via the mint CAS).
- **TON donations** — `src/subscription-core.ts` polls TON, matches the **bound** wallet
  and credits `Donation` votes. Donation target = `COLLECTION_OWNER`
  (exposed by `GET /api/public/config`).
- **Stars top-up** — `POST /api/users/topup/invoice` creates an `XTR` invoice with a
  tamper-proof payload (`cube-topup:<userId>:<stars>:<votes>` round-trips through
  Telegram); the bot's `topup` feature answers `pre_checkout_query` and credits on
  `successful_payment`, idempotent on the unique `StarsPurchase.chargeId`
  (record-then-credit — replays are no-ops).

### Wallet binding (TON Connect ton_proof)
`POST /api/auth/wallet-nonce` issues a stateless HMAC nonce (5-min TTL, bound to userId)
→ the frontend passes it via `setConnectRequestParameters` → the wallet signs during
connect → `POST /api/auth/set-wallet` verifies in `ton-proof.ts` (payload HMAC + expiry
+ userId + domain + stateInit-hash + Ed25519 signature).

### Login
`POST /api/auth/login` upserts the user, syncs `user.name` from initData (`username` →
`first_name` — nothing else sets it for webview-only users), captures the referrer, and
returns `{ balance, minted, mintState, wallet }`.

## Configuration

- `.env` is required for runtime secrets and service endpoints (see `.env.example`).
- Core config lives in `src/config.ts` using `znv` with Zod schemas.
- Config uses a lazy proxy singleton — first property access triggers initialization.
- In test mode (`NODE_ENV=test`), the config Proxy **throws on any property read** —
  modules a test imports must not touch `config.X` at load time (hence the pure-handler
  + composer split pattern).
- v3 economy knobs (all optional): `GENERATION_TRY_COST_VOTES` (100),
  `STARS_TOPUP_VOTES_PER_STAR` (10), `REFERRAL_MINT_REWARD_VOTES` (200).

## Integration Points

- **Telegram Bot API** via Grammy (polling or webhook) — also used server-side to list
  and download profile photos for the avatar picker.
- **TON blockchain** via @ton/ton for donation monitoring and NFT minting.
- **TonConnect** for wallet connection + ton_proof binding in the frontend.
- **Telegram Stars** (`XTR`) for $CUBE top-ups.
- **Pinata** for IPFS storage of NFT metadata and images.
- **Stability AI** for image-to-image generation (pixel-art artwork).
- **OpenAI** for the pass description text.

## Build and Deployment

- **Dev:** `npm run dev` (landing build + tsx watch) serves the full app at :3000 — vite
  runs as Fastify middleware with HMR, dynamically imported from
  `src/frontend/node_modules` (two copies of rolldown's native binding in one process
  segfault on dlopen). `npm --prefix src/frontend run dev` is an optional frontend-only
  server (:5173, no /api).
- **Build:** `npm run build:all` → tsc (backend) + landing generator + vite (frontend).
- **Production:** multi-stage Docker image (Node 22 slim; builder compiles the frontend
  and landing, runner installs prod deps only — `tsx` is a prod dependency and runs
  `src/` directly) behind kamal-proxy. Deployed with Kamal: `kamal deploy` → production
  (cubeworlds.club), `kamal deploy -d staging` → the staging bot @cubeworldsbot at
  staging.cubeworlds.club (`config/deploy.staging.yml`: own service name, Mongo DB and
  data volume; `.kamal/secrets.staging` overrides only the bot token, webhook and DB).
  `/tonconnect-manifest.json` is generated from `WEB_APP_URL` so ton_proof's domain
  check holds on either host.
- **Pre-deploy gates:** `npm run smoke:api` (boots the real app with fake secrets against
  a throwaway Mongo and drives the API end-to-end) and
  `CHECK_MONGO_URI=… npx tsx scripts/check-prod-users.ts` (read-only v1-database
  compatibility check: duplicate wallets/ids, BigInt-castability of votes, state enum).
- **CI** (`.github/workflows/main.yml`): lint + typecheck + frontend build,
  backend tests, and the API smoke — on every push/PR.

## Security Architecture

- **Auth:** all authenticated endpoints validate Telegram `initData` signatures
  (HMAC, 24h expiry).
- **Wallet binding:** TON Connect ton_proof — stateless HMAC nonce + Ed25519 signature
  verification; each rebind needs a fresh, userId-bound nonce (no replay across accounts).
- **Economy:** overdraft-safe `$gte` debit CAS for paid tries; append-only ledger with
  compensating writes on partial failure; Stars credits idempotent on
  `telegram_payment_charge_id`; referral reward gated by human mint approval.
- **NFT mint:** admin-only authz, CAS mint-claim (`mintingInProgress`) → single mint on
  double-approve; mint-before-flip biases rare crashes toward false-error, never
  double-mint.
- **Upload boundary:** JPEG/PNG mime allowlist + 8 MB multipart limit + jimp re-encode
  to PNG (strips whatever the client claimed the file was).
- **Path safety:** file ops sanitize usernames and verify resolved paths stay within
  `./data/` (`src/common/helpers/files.ts`).
- **Rate limits:** per-route overrides in `server.ts` (`/api/mint/generate` 6/min — it's
  a paid Stability call); bounded leaderboard pagination.
- **Claim locking:** in-process promise chain prevents concurrent double-claims
  (single-instance only).

## Conventions

- ESM-only imports (no CommonJS). No semicolons, single quotes, 2-space indent.
- Type imports sorted before value imports (perfectionist/sort-imports).
- Keep frontend and backend dependencies isolated (separate `package.json`).
- Backend handlers use the dependency-injection pattern for testability;
  config-touching modules split into a pure `foo-handler.ts` + a `foo.ts` composer.
- bigint never crosses a JSON boundary — always `.toString()` in responses.
- Avoid editing generated output under `build/`, `src/frontend/dist/`, `src/landing/dist/`.
